# Отчет по проекту BauTex Design

## 1. Общая характеристика проекта

BauTex Design - веб-приложение для подбора и заказа жаккардовых обоев из кварцевой нити под покраску. Проект объединяет функции сайта-витрины, каталога товаров, личного кабинета, административной панели и ML-инструмента для визуализации обоев в интерьере.

Главная идея проекта - дать пользователю не только посмотреть обои в каталоге, но и примерить их на фотографию своей комнаты. Для этого реализован pipeline компьютерного зрения: пользователь загружает фото, система выделяет стену, строит маску и накладывает выбранные обои с выбранным цветом на выделенную область.

Проект состоит из трех основных частей:

- frontend: React + TypeScript + Webpack;
- backend: Express + SQLite в папке `server`;
- ML-сервис: FastAPI + SegFormer B0 в папке `ml_service`.

Такое разделение хорошо подходит для дипломной работы. Frontend отвечает за пользовательский интерфейс, backend - за бизнес-логику, авторизацию, заказы, файлы и сохранение данных, а ML-сервис отдельно решает задачу сегментации стен.

## 2. Цель проекта

Цель проекта - разработать интерактивную веб-систему для выбора обоев, которая помогает пользователю принять решение о покупке через визуальную примерку материала в реальном помещении.

Практическая цель:

- представить ассортимент обоев;
- дать пользователю каталог, коллекции, избранное и оформление заказа;
- рассчитать примерное количество рулонов;
- сохранить результаты визуализации;
- дать администратору базовое управление пользователями, заказами и обращениями.

Исследовательская цель:

- изучить способы автоматического выделения стен на фото;
- выбрать подходящий метод сегментации;
- реализовать pipeline “фото -> маска стены -> наложение обоев”;
- подготовить базу для оценки качества сегментации через IoU, Dice, precision и recall.

## 3. Целевая аудитория

Пользователи проекта:

- частные покупатели, которые делают ремонт;
- дизайнеры интерьера;
- мастера и отделочники;
- менеджеры компании;
- администратор сайта.

Для покупателей важны понятный каталог, цена, расчет количества рулонов и возможность увидеть результат в своей комнате. Для дизайнера важна визуальная примерка и сохранение нескольких вариантов. Для администратора важны заказы, пользователи, обращения и контроль статусов.

## 4. Основные пользовательские сценарии

Основной сценарий пользователя:

1. Пользователь открывает сайт.
2. Изучает главную страницу, преимущества, отзывы и инструкции.
3. Переходит в каталог или коллекции.
4. Фильтрует товары по коллекции, стилю и цене.
5. Открывает карточку товара.
6. Добавляет товар в избранное или корзину.
7. Переходит в визуализацию.
8. Загружает фото комнаты.
9. Выбирает обои и цвет.
10. Получает результат “до / после”.
11. Сохраняет или печатает результат в PDF.
12. Оформляет заказ с расчетом площади и рулонов.
13. Видит заказ и визуализации в личном кабинете.

Сценарий администратора:

1. Администратор входит под ролью `admin`.
2. Открывает личный кабинет.
3. Видит список пользователей.
4. Ищет пользователя или заказ через поиск.
5. Просматривает заказы.
6. Меняет статус заказа.
7. Просматривает обращения поддержки.
8. Отвечает пользователю и закрывает обращение.

## 5. Структура frontend

Frontend реализован на React и TypeScript. В проекте используется маршрутизация через React Router, состояние авторизации и избранного хранится через Redux Toolkit, а сборка выполняется Webpack.

Ключевые страницы:

- `/` - главная страница;
- `/catalog` - каталог товаров;
- `/favorites` - избранное;
- `/account` - личный кабинет и админ-панель;
- `/visualization` - визуализация обоев в комнате;
- `/ai-chat` - AI-чат;
- `/where-to-buy` - карта и список точек;
- `/info/how-to-paint` - инструкция по покраске;
- `/info/how-to-glue` и `/info/how-to-paste` - инструкция по поклейке;
- `/collections/...` - страницы коллекций.

Тяжелые страницы подключены через `React.lazy` и `Suspense`. Это уменьшает нагрузку на начальный маршрут и делает главную страницу быстрее.

## 6. Каталог и коллекции

Каталог хранит товары в `src/data/catalogItems.ts`. У товаров есть:

- артикул;
- название;
- описание;
- коллекция;
- изображение;
- цена;
- размер рулона;
- плотность;
- доступные цвета.

Добавлены фильтры:

- поиск по артикулу, названию и описанию;
- фильтр по коллекции;
- фильтр по стилю;
- цена от / до;
- сортировка.

Это улучшает пользовательский сценарий: покупателю не нужно просматривать весь список вручную, он может быстро найти подходящий вариант.

Новые изображения обоев были сжаты и разложены по рабочим папкам:

- `src/assets/fabrics/wallpapers` - изображения для frontend-каталога;
- `server/public/wallpapers` - изображения для backend-визуализации.

Такой подход позволяет использовать реальные обойные фактуры вместо случайных интерьерных картинок.

## 7. Оформление заказа и расчет рулонов

В форме заказа пользователь вводит город, тип ткани, цвет, площадь и контактные данные. На основе площади рассчитывается стоимость материала и доставка.

Добавлен расчет рулонов:

- базовый размер рулона: `1.06 x 10 м`;
- площадь рулона: примерно `10.6 м²`;
- запас: `10%`;
- количество рулонов считается через округление вверх.

Формула:

```text
площадь_с_запасом = площадь * 1.1
количество_рулонов = ceil(площадь_с_запасом / 10.6)
```

Расчет находится именно в оформлении заказа, потому что пользователь вводит площадь на этом этапе. Это логичнее, чем держать расчет отдельно: пользователь сразу видит и цену, и примерное количество рулонов.

Backend реализован на Express. Он находится в папке `server` и считается единственным актуальным backend проекта.

Backend отвечает за:

- регистрацию;

- роли `user` и `admin`;
- заказы;

- отзывы;
- обращения поддержки;

- загрузку фото;

Основные API:

- `GET /api/orders/my`;

В качестве базы данных используется SQLite. Для дипломного проекта это практично: база не требует отдельного сервера, быстро запускается локально и подходит для демонстрационного прототипа.

Основные таблицы:

Таблица `visualizations` хранит:

Это полезно и для пользователя, и для диплома: можно показывать историю результатов и собирать данные о работе алгоритма.

## 10. Авторизация и роли

В проекте реализованы роли:

- `user` - обычный пользователь;
- `admin` - администратор.

Регистрация создает обычного пользователя. Администратор задается через переменные окружения `ADMIN_EMAIL` и `ADMIN_PASSWORD`. При запуске backend синхронизирует пароль и роль администратора.

Админские маршруты защищены middleware `requireAdmin`. Это важно: доступ ограничен не только на уровне интерфейса, но и на уровне backend. Обычный пользователь не может получить список всех пользователей или заказов прямым API-запросом.

## 13. Рассмотренные варианты визуализации

Для задачи автоматического выделения стены были рассмотрены несколько подходов.

### Простое наложение

Самый простой вариант - растянуть текстуру обоев на всю фотографию и смешать с исходным изображением. Он быстрый, но не подходит как основная функция, потому что обои попадают на мебель, пол, окна и предметы.

Вывод: подходит только как аварийный fallback.

### Ручная кисть

Пользователь сам закрашивает стену, а система накладывает обои по ручной маске.

Плюсы:

- не нужен ML;
- работает локально;
- точность зависит от пользователя;
- удобно для коррекции.

Минусы:

- занимает время;
- неудобно на маленьких экранах;
- не выглядит как интеллектуальная функция.

Вывод: оставить как fallback и коррекцию.

### Эвристическая сегментация

Эвристика анализирует цвет, яркость, контраст и положение пикселей. Стены часто имеют большую ровную область, поэтому можно попробовать построить маску по статистике изображения.

Плюсы:

- быстро;
- локально;
- без модели.

Минусы:

- плохо работает на сложных интерьерах;
- путает стены и мебель похожего цвета;
- не понимает семантику объектов.

Вывод: подходит как fallback без ML-сервиса.

### Background removal API

Можно использовать внешние сервисы удаления фона. Но задача удаления фона не равна задаче поиска стены. Такие API часто выделяют объект переднего плана, а не стену.

Минусы:

- нужны ключи;
- есть зависимость от интернета;
- фото отправляется внешнему сервису;
- результат не оптимален для класса wall.

Вывод: не лучший вариант для дипломного проекта.

### U-Net

U-Net подходит для сегментации, но требует собственного размеченного датасета и обучения.

Вывод: хороший научный вариант, но слишком дорогой по времени для текущего прототипа.

### DeepLabV3+

DeepLabV3+ - сильная архитектура сегментации, но интеграция готовой модели под класс стены менее удобна для быстрого локального прототипа.

Вывод: технически подходит, но SegFormer удобнее.

### Mask R-CNN

Mask R-CNN решает instance segmentation, то есть выделяет отдельные объекты. Стена чаще является поверхностью сцены, а не отдельным объектом.

Вывод: не лучший тип модели для задачи wall segmentation.

### Segment Anything Model

SAM хорошо выделяет области по подсказке: клику, точке или рамке. Он может быть полезен для будущего режима “кликни по стене”, но базовый SAM не знает автоматически, какой сегмент является стеной.

Вывод: перспективно для будущего интерактивного уточнения, но не как основной простой pipeline.

### SegFormer

SegFormer решает семантическую сегментацию. Выбран вариант `nvidia/segformer-b0-finetuned-ade-512-512`, потому что он обучен на ADE20K, где есть классы сцен, включая стены.

Плюсы:

- модель уже знает класс wall;
- не нужно обучать модель с нуля;
- B0-версия относительно легкая;
- можно запустить локально;
- хорошая дипломная объяснимость;
- фото не отправляются внешнему API.

Вывод: выбран как основной вариант.

### Дополнительный дипломный анализ: сравнение ML-подходов

Для дипломной работы важно не просто назвать выбранную модель, а показать, что задача была разложена на несколько технических этапов и для каждого этапа были рассмотрены альтернативы.

#### Постановка задачи

В проекте не требуется генерировать новые обои с нуля. Обои уже существуют в каталоге как конкретные текстуры и изображения. Поэтому задача состоит из двух частей:

1. Найти на фотографии область стены и не затронуть мебель, окна, пол, потолок и декоративные предметы.
2. Наложить выбранную текстуру обоев на найденную область так, чтобы сохранить общий вид комнаты, тени и ощущение поверхности.

Это важное отличие от генеративной задачи. Если использовать только диффузионную модель, она может создать красивую стену, но исказить реальный рисунок обоев из каталога. Для интернет-магазина это плохо: пользователь должен видеть именно выбранный товар, а не похожую сгенерированную фантазию.

#### Критерии выбора метода

Для сравнения методов использовались следующие критерии:

- умеет ли метод выделять именно стены;
- требуется ли собственный размеченный датасет;
- можно ли запустить решение локально;
- насколько сложно интегрировать метод в веб-приложение;
- насколько хорошо метод объясняется в дипломной работе;
- сохраняет ли подход исходную текстуру товара;
- зависит ли решение от платных внешних API;
- насколько быстро оно работает на обычном компьютере.

#### Сравнение методов сегментации стен

| Метод | Сильные стороны | Ограничения для проекта | Итог |
|---|---|---|---|
| Ручная кисть | Максимально контролируемый результат, не нужен ML | Пользователь тратит время, функция выглядит менее интеллектуальной | Оставлена как fallback и коррекция |
| Эвристика по цвету и контрасту | Быстро, локально, без модели | Не понимает смысл объектов, путает стену и мебель похожего цвета | Оставлена как fallback без ML-сервиса |
| U-Net | Классическая архитектура для сегментации, хорошо подходит для обучения на своем датасете | Нужны размеченные изображения стен и обучение модели | Хороший исследовательский вариант, но не быстрый путь для прототипа |
| PSPNet | Учитывает глобальный контекст сцены | Модель тяжелее и менее удобна для быстрой интеграции | Можно рассматривать теоретически |
| DeepLabV3+ | Сильная архитектура семантической сегментации, хорошие границы | Для задачи wall нужен подходящий pretrained-вариант или дообучение | Достойная альтернатива SegFormer |
| Mask R-CNN | Хорошо выделяет отдельные объекты | Стена чаще является областью сцены, а не отдельным объектом-instance | Не основной выбор |
| YOLOv8-seg | Быстро работает, удобно для объектов | Нужен датасет с классом стены, сегментация больше instance/object-oriented | Подходит хуже, чем semantic segmentation |
| SAM | Очень сильная promptable-сегментация, хорош для клика/рамки | Базовый SAM не знает, что именно является стеной, ему нужна подсказка | Хорош для будущей функции “уточнить стену кликом” |
| Mask2Former | Современная универсальная архитектура сегментации | Более тяжелая интеграция, выше требования к ресурсам | Сильная альтернатива для продвинутой версии |
| OneFormer | Универсальная модель для semantic/instance/panoptic segmentation | Сложнее, тяжелее и избыточнее для дипломного прототипа | Перспективно, но не выбрано |
| SegFormer | Semantic segmentation, есть готовые ADE20K-веса, есть класс wall, удобно запускать через Hugging Face | B0 легче, но менее точен, чем B5; возможны ошибки на сложных фото | Выбран как основной метод |

#### Почему выбран SegFormer

SegFormer выбран не потому, что он “абсолютно лучший из всех существующих моделей”, а потому что он дает лучший баланс для данного проекта:

- решает именно semantic segmentation, а не просто выделение любого объекта;
- pretrained-модели на ADE20K уже знают интерьерные классы, включая стены;
- не требует собирать большой собственный датасет на первом этапе;
- B0-версия достаточно легкая для локального FastAPI-сервиса;
- модель можно объяснить в дипломе через понятный pipeline “фото -> карта классов -> маска wall”;
- пользовательское фото не уходит в платный внешний API;
- результат можно измерять через IoU, Dice, Precision и Recall.

В отчете можно отдельно указать, что более тяжелая модель `nvidia/segformer-b5-finetuned-ade-640-640` потенциально может дать более высокое качество, но для локального прототипа выбрана B0-версия как более быстрая и простая в запуске. Для диплома это нормальная инженерная позиция: сначала реализуется рабочий pipeline на легкой модели, затем качество можно улучшать заменой B0 на B2/B5 или дообучением на собственном датасете.

#### Сравнение методов наложения текстуры

После получения маски стены нужно решить вторую задачу: как перенести выбранные обои на фотографию комнаты.

| Метод | Сильные стороны | Ограничения для проекта | Итог |
|---|---|---|---|
| Простое alpha-blending наложение | Быстро, прозрачно, сохраняет выбранную текстуру | Не учитывает перспективу и сложное освещение | Используется как базовая реализация |
| Multiply/soft-light compositing | Лучше сохраняет тени и фактуру исходного фото | Не решает геометрию стены полностью | Подходит для текущего прототипа |
| Poisson blending | Хорошо сглаживает границы вставки | Может размывать или менять рисунок обоев | Можно использовать как улучшение границ |
| Гомография / perspective transform | Позволяет подогнать текстуру под плоскость стены | Нужно определить углы/плоскость стены | Хороший следующий шаг |
| Intrinsic image / relighting | Теоретически лучше сохраняет освещение | Сложно для реализации и объяснения в прототипе | Перспектива для будущей версии |
| GAN-based image translation | Может давать реалистичный результат | Требует датасета и может менять товарную текстуру | Не выбран |
| Stable Diffusion Inpainting | Фотореалистично дорисовывает область | Может галлюцинировать и изменить реальные обои | Хорошо как исследовательская альтернатива |
| ControlNet MLSD + Inpainting | Лучше сохраняет линии, проемы и геометрию | Тяжелее, медленнее, требует GPU, может менять паттерн | Перспективно, но не основной выбор для каталога |

#### Почему не выбран Stable Diffusion Inpainting + ControlNet как основа

Предложение “Stable Diffusion Inpainting + ControlNet MLSD” технически сильное и его стоит упомянуть в дипломе как перспективную альтернативу. Такой подход может лучше сохранять геометрию комнаты, линии, проемы и общий фотореализм.

Но для текущего сайта есть важные минусы:

- диффузионная модель может изменить рисунок выбранных обоев;
- пользователю каталога важно видеть конкретный товар, а не похожую генерацию;
- локальный запуск требует больше ресурсов, желательно GPU;
- время обработки выше;
- сложнее гарантировать повторяемость результата;
- сложнее объяснить, почему итоговая картинка соответствует именно выбранной позиции каталога.

Поэтому в текущем проекте выбран более контролируемый подход: SegFormer строит маску стены, а backend накладывает конкретную текстуру из каталога через deterministic image processing. Это менее “магически” выглядит, зато лучше соответствует задаче интернет-магазина и проще проверяется.

#### Итоговое обоснование выбора

Итоговый выбор:

- сегментация стены: локальный FastAPI + SegFormer B0;
- fallback: эвристическая маска и ручная кисть;
- наложение: масштабирование выбранной текстуры, цветовой tint и смешивание с исходным фото по маске;
- оценка качества: IoU, Dice, Precision, Recall на тестовом наборе фото.

Такой выбор является рациональным для дипломного прототипа: система работает локально, не зависит от платных API, сохраняет выбранную текстуру обоев и имеет измеримые метрики качества. В разделе перспектив можно указать улучшения: SegFormer B5, Mask2Former, SAM для уточнения кликом, perspective transform и отдельный эксперимент со Stable Diffusion Inpainting + ControlNet.

## 14. Выбранный pipeline визуализации

Итоговый pipeline:

```text
фото -> Express backend -> FastAPI SegFormer -> маска стены -> наложение обоев и цвета -> результат
```

Если SegFormer недоступен:

```text
фото -> эвристическая маска -> наложение -> предупреждение о качестве
```

Если пользователь включает кисть:

```text
фото -> ручная маска -> наложение обоев -> результат
```

Итоговая система является гибридной: основная функция - автоматическая сегментация SegFormer, резерв - эвристика, коррекция - ручная кисть.

## 15. ML-сервис

ML-сервис реализован на FastAPI. Он находится в `ml_service/app.py`.

Endpoint:

- `GET /health`;
- `POST /segment/wall`.

Сервис:

1. Загружает изображение.
2. Преобразует его в RGB.
3. Передает изображение в SegFormer.
4. Получает карту классов.
5. Выбирает классы, соответствующие стенам.
6. Строит бинарную маску.
7. Применяет постобработку.
8. Возвращает PNG-маску.

Постобработка включает медианный фильтр, размытие и threshold. Это уменьшает шум и делает маску стабильнее.

Текущие ограничения:

- SegFormer B0 не дообучен на собственном датасете BauTex;

- маска может ошибаться на сложных фото;
- кисть работает как коррекция, но требует ручного действия;
- backend-корзина уже реализована для авторизованных пользователей, но гостевая корзина все еще может использовать localStorage;
- управление каталогом из админки реализовано базово: можно создать, отредактировать и скрыть товар, но пока нет полноценной медиатеки и модерации коллекций;

- нет CI pipeline;
- production-хранение файлов пока не реализовано;
- часть старых текстов и комментариев в коде может требовать дальнейшей чистки кодировки.

### 22.7. Исправления после ручной проверки интерфейса

После проверки в браузере были исправлены четыре проблемы.

1. Метки на Яндекс Картах не открывали баллуны стабильно, потому что карта пересоздавалась после клика по метке. Логика инициализации карты отделена от выбора активной точки, поэтому клик по метке теперь не уничтожает экземпляр карты.

2. Корзина приведена к той же логике доступа, что и избранное. Теперь неавторизованный пользователь не может добавлять товары в корзину локально: корзина хранится на backend и требует входа в аккаунт.

3. Для автоматической визуализации выявлена причина плохой маски: при недоступном `SEGFORMER_API_URL` использовался локальный fallback. Fallback-маска уточнена, а локальный FastAPI-сервис SegFormer поднят на `http://localhost:8000`.

4. Наложение обоев изменено с растягивания одной картинки на повторяющийся паттерн. Это сохраняет масштаб фактуры: обои повторяются плиткой, а не превращаются в одно большое изображение на всю стену. В интерфейс добавлен слайдер масштаба принта.

### 22.9. Сравнение методов сегментации для отчета

Для дипломной работы были рассмотрены несколько подходов к выделению стен на фотографии интерьера.

| Метод | Сильные стороны | Ограничения | Вывод |
| --- | --- | --- | --- |
| U-Net | Простая и понятная архитектура, хорошо подходит для бинарных масок | Требует собственного размеченного датасета стен и обучения | Подходит для будущего дообучения, но не лучший быстрый выбор для прототипа |
| PSPNet | Хорошо учитывает глобальный контекст сцены | Тяжелее объяснять и интегрировать, менее удобна для локального быстрого запуска | Рассмотрена как альтернатива семантической сегментации |
| DeepLabV3+ | Высокое качество границ и сильная семантическая сегментация | Более тяжелая интеграция, выше требования к ресурсам | Достойная альтернатива, но сложнее для дипломного прототипа |
| SAM | Очень сильная универсальная сегментация объектов | Не знает класс "стена" без подсказки, требует prompt/клик/box | Полезен как будущая функция выбора стены кликом |
| Mask2Former | Современная универсальная архитектура для semantic/instance/panoptic segmentation | Тяжелее SegFormer, сложнее локальный запуск | Качественная альтернатива, но избыточна для текущего прототипа |
| OneFormer | Универсальная модель для нескольких типов сегментации | Высокая сложность и вес модели | Перспективна для исследования, но не для базовой реализации |
| YOLOv8-seg | Быстрая instance segmentation | Обычно работает с объектами, а не с семантическим классом "стена" | Не оптимален для выделения стен как фоновой поверхности |
| SegFormer B0 | Есть готовые веса ADE20K, модель знает класс wall, локально запускается через FastAPI | Может ошибаться на сложных интерьерах, требует fallback и ручной коррекции | Выбран как основной метод из-за баланса качества, скорости и объяснимости |

Итоговое решение: локальный FastAPI + SegFormer B0 для основной автоматической сегментации, fallback-эвристика для отказоустойчивости и ручная кисть для коррекции результата пользователем. Такой набор достаточен для дипломного прототипа, потому что в проекте есть рабочий ML-pipeline, метрики, обработка ошибок и сравнение с альтернативами.

## 23. Итог

BauTex Design стал полноценным прототипом интерактивной системы подбора обоев. В проекте есть витрина, каталог, коллекции, избранное, корзина, оформление заказа, расчет рулонов, личный кабинет, админ-панель, поддержка, AI-чат, ML-визуализация, сохранение результатов и Docker-инфраструктура.

Для дипломной работы особенно важна визуализация. Были рассмотрены разные методы: простое наложение, ручная кисть, эвристика, background removal API, U-Net, DeepLabV3+, Mask R-CNN, SAM и SegFormer. В качестве основного решения выбран локальный FastAPI + SegFormer B0, потому что он решает именно семантическую сегментацию, знает класс стены, работает локально и хорошо объясняется в рамках диплома.

Проект имеет понятную практическую ценность и хороший исследовательский потенциал. Его можно развивать как в сторону пользовательского продукта, так и в сторону научной части: сбор датасета, расчет метрик, сравнение моделей и повышение реалистичности наложения.
